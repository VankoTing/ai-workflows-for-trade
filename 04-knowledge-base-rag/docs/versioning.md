# 文档版本与时效管理（Temporal RAG）

> 解决的问题：**知识会过期，但向量检索不知道。**
> 26 年换了供应商、调了价格，新价格表和旧价格表同时躺在库里，
> 检索时只看"语义像不像"，不看"哪个才是当前有效的" —— 于是答错。

本文件定义三件事：
1. **版本与时效标记**（给每份资料打上时间属性）
2. **检索时按时间过滤**（默认只答"当前有效"的知识）
3. **质量衰减自动诊断**（主动发现冲突、过期、重复）

---

## 一、术语（说人话）

| 术语 | 含义 |
|---|---|
| **时效性 Temporal** | 一条知识"什么时候有效"。价格表 2025 版在 2026 年就失效了 |
| **版本 Version** | 同一份资料的第几版。`Rev.4` 就是第 4 版 |
| **文档家族 doc_family** | 逻辑上是"同一份东西"的所有版本。`product catalog` 的 2024 版和 2026 版属于同一个家族 |
| **生效 / 失效日期** | effective_from / effective_to。有效期是一个区间 |
| **当前版本 current** | 在"今天"这个时点有效的那一版 |
| **时间旅行 as-of** | 按指定日期查询："**2025 年 6 月**这个型号卖多少钱？" |
| **质量衰减 Decay** | 资料随时间推移而"可信度下降"——不是因为错，而是因为**可能已过时** |
| **冲突 Conflict** | 同一家族下**存在多个同时有效的版本**，且内容不一致 |
| **知识血缘 Provenance** | 一条回答背后引用的是哪个版本、什么日期。**可追溯才好追责** |

---

## 二、元数据字段（每个切片都带）

| 字段 | 类型 | 说明 |
|---|---|---|
| `doc_family` | str | 文档家族 ID（同一份资料的不同版本共享同一个值） |
| `version` | str | 版本标识：`Rev.4` / `v6` / `2026` / 自动序号 |
| `version_rank` | int | 可比较的版本序号（用于排序找最新） |
| `doc_date` | int | 业务日期，格式 `YYYYMMDD`（如 `20260831`） |
| `doc_date_src` | str | **日期是怎么来的**（可追溯，见下节） |
| `effective_from` | int | 生效日期 `YYYYMMDD` |
| `effective_to` | int | 失效日期 `YYYYMMDD`；`0` 表示"至今有效" |
| `status` | str | `active` / `superseded` / `archived` |
| `age_days` | int | 距今多少天（生成报告时算，便于诊断） |
| `dup_of` | str | 若内容与其他文件重复，指向"主副本"的 source |

> ⚠️ **为什么日期要存成整数 `YYYYMMDD`？**
> 向量库（Chroma）的过滤条件只支持**数值比较**，不支持日期类型。
> 转成整数后，`effective_from <= 20261013` 这种比较才能下推到数据库里。
> 这一步必须在**写入时**做好，检索时才过滤得动。

## 三、日期从哪来（可信度分级）

从高到低，取第一个命中的：

| 优先级 | 信号 | 例子 → 结果 | 可信度 |
|---|---|---|---|
| 1 | 文件名 `Rev.N` / `(N)` | `PRICE...vs Italy(6).xlsx` | 版本号，不直接是日期 |
| 2 | 目录名 8 位日期 | `20260831-某地区/` → `20260831` | **高** |
| 3 | 文件名 8 位日期 | `20260515sunny.xlsx` → `20260515` | **高** |
| 4 | 文件名 6 位日期 | `250715-报价.xlsx` → `20250715` | 中（易误判，需年份合理） |
| 5 | 文件名 4 位年份 | `product catalog_2024.pdf` → `2024xxxx` | 中（只知年） |
| 6 | **文件 mtime** | 系统时间 | 中低（拷贝会失真，本库未失真） |
| 7 | 内容里的日期 | 报价单里的 "Date:/有效期至" | 高但成本高（留阶段二） |

**必须记录 `doc_date_src`**（`dir` / `filename` / `mtime` / `content`）：
面试或审计时能回答"这个日期是**读出来的**还是**猜的**"。

**实测覆盖率**（本项目）：
- 目录名含 8 位日期：**49 / 133** 个报价目录
- 文件名含日期：**250 / 1219**
- 文件 mtime 保留原始时间（跨度 2017→2026，2025+2026 占 **94%**）
- → 精确日期约 20%，其余用 mtime 兜底，**覆盖率 100%**，但可信度分层。

## 四、文档家族（doc_family）怎么分

| 场景 | 分组规则 | 例子 |
|---|---|---|
| 报价单目录 | `INQ:{开头数字}` | `0190045-业务员` → `INQ:0190045` |
| 通用资料 | 文件名主干（去掉日期/版本后缀） | `product catalog_2024.pdf` / `product catalog.pdf` → 同一个 family |
| 其余 | 所在目录 + 去后缀文件名 | 兜底 |

**去后缀规则**（把"同一份东西的不同版本"归到一起）：
```
product catalog_2024.pdf      → product catalog
product catalog.pdf           → product catalog
PRICE Germany vs Italy(6).xlsx → PRICE Germany vs Italy
Valve List-Q250609 Rev.4.xlsx  → Valve List-Q250609
```
即：剥掉 `_2024` / `-2024.06` / `(N)` / `Rev.N` / `vN` / `副本` 等版本标记。

## 五、状态判定（谁是"当前版本"）

判定分四步，**越往后越保守**：

```
① 全局去重   内容指纹相同的文件 → 除"主副本"外标 duplicate
             （**跨家族**做，因为同一份文件常被改名 —— 实测漏了 55 组；
               主副本优先选「人工保留 > 产品资料/ 目录 > 路径短」）

② 版本取代   同一 family 内，"内容不同 + 双方日期来源可信 + 相差 ≥30 天"
             → 旧的标 superseded

③ 其余       一律保持 active → 进诊断报告列成「待裁决冲突」
             （"哪一版作数"是业务决策，程序不擅自判死）

④ 人工裁决   若存在 data/version_decisions.json → 覆盖以上结论：
             选中的 active、同族其余 rejected；选「全部保留」则整族 active
```

| 状态 | 含义 | 默认检索是否命中 |
|---|---|---|
| `active` | 当前有效 | ✅ |
| `duplicate` | 内容与其他文件完全相同（副本） | ❌ |
| `superseded` | 已被新版本取代（程序判断） | ❌ |
| `rejected` | **被人工否决** | ❌ |

**冲突判定**：同一 family 下有 ≥2 个 `active` → 进诊断报告等人工裁决。
（这正是你担心的场景：两份价格表都在，但不一致。）

## 六、检索时的过滤

| 查询方式 | 过滤条件 | 用途 |
|---|---|---|
| **默认**（推荐） | `status = active` | 只答当前有效知识，**默认不掉进旧版本的坑** |
| **时间旅行** | `effective_from <= T` 且 `status != duplicate` | "2025 年 6 月这个型号多少钱？" |
| **全量/考古** | 无过滤 | 排查问题、对比历史 |

实现要点：Chroma 的 `where` 里用 `$and` 组合，数值比较下推给数据库。

### 另一道闸门：同一文件不霸占名额

就算版本过滤做对了，还有一类"稀释"：**一份几十页的手册会产生几十个切片**，
语义检索会把它的段落一片片排到前面，把其他资料全挤下去。

对策：`--max-per-doc N`（默认 2）—— 同一份文件最多贡献 N 条，
让结果覆盖更多**不同**的资料。

> 实测：取 6 条结果，未限流时只来自 3~4 个文件；限流后 **覆盖 6 个不同文件**。

## 七、质量衰减自动诊断（`scripts/age_report.py`）

输出四类问题：

| # | 诊断项 | 判定规则 | 应对 |
|---|---|---|---|
| 1 | **过期预警** | `active` 且 `age_days > 365` | 提示人工确认是否已换版 |
| 2 | **版本冲突** | 同一 family 有 ≥2 个 `active` | **最高优先级**，需业务裁决哪份作数 |
| 3 | **重复冗余** | 多份文件内容哈希相同，散落不同目录 | 保留一份为"主副本"，其余标 `dup_of` |
| 4 | **更新缺口** | 关键类型（价格表/产品目录）最新版本 `age_days > 180` | 提醒补充新资料 |

**整体健康度**用一个 0-100 的"时效健康分"表示（看板上可视化）。

## 八、人工裁决闭环（"哪一版作数"交给人）

自动判定只敢处理"铁证"情形。剩下的冲突**必须由业务裁决** —— 因为只有业务知道
"26 年是不是换了供应商""这份报价还算不算数"。

**闭环流程**：

```
scripts/age_report.py            ① 扫出冲突家族      → data/age_report.json
        ↓
scripts/build_review_sheet.py    ② 生成可点选的裁决表  → dashboard/review.html
        ↓                              （系统预选建议项，人只需确认或改）
   人在浏览器里逐条确认，点「导出裁决结果」
        ↓
   version_decisions.json 放到 data/
        ↓
scripts/backfill_time_meta.py    ③ 应用裁决，刷新状态
        ↓
   检索立刻遵守：选中的 → active，同族其余 → rejected（默认检索不再命中）
```

**裁决文件格式**（`data/version_decisions.json`）：

```json
{
  "generated": "2026-10-13 09:00",
  "decisions": {
    "product catalog": { "keep": "产品资料/product catalog_2026.pdf", "action": "keep_one" },
    "globe valve":     { "keep": "__all__", "action": "keep_all" }
  }
}
```

| action | 含义 | 效果 |
|---|---|---|
| `keep_one` | 保留指定的那一份 | 选中的 `active`，同族其余 `rejected` |
| `keep_all` / `keep="__all__"` | 它们不是版本关系，各自都有用 | 整族都置 `active` |
| `skip` | 暂不裁决 | 保持程序原判定 |

> **优先级**：人工裁决 > 自动判定。`assign_status()` 最后一步会应用裁决文件。
> 这也体现了一条原则：**程序负责把问题摆到人面前，不替人做业务决定。**

### 设计上的两个贴心点

1. **给建议、不是给任务** —— 每个家族预先选中"日期最新/来源可信"的那份，
   用户可以一键「全部采纳系统建议」，只对少数有疑问的逐条修改。
2. **按优先级分组** —— 高优先（含目录名/文件名日期，最可能是真版本关系）58 个、
   中（只有 mtime 但有日期差）28 个、低（日期几乎相同）15 个。先看高优先即可。
