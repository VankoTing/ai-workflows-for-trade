## L01 · Ollama 拉模型报 `resolves to non-public 198.18.0.244`

| 项 | 内容 |
| --- | --- |
| **现象** | `ollama pull qwen2.5:7b` 报错：`redirect target not allowed: ...r2.cloudflarestorage.com resolves to non-public 198.18.0.244` |
| **排查过程** | 逐个域名做 DNS 解析，发现 `registry.ollama.ai`→198.18.0.243、`ollama.com`→198.18.0.232，**连 `baidu.com` 都→198.18.0.246** |
| **根因** | 代理软件开了 **fake-ip 模式**：把所有域名都虚拟成 `198.18.0.0/15` 段地址。Ollama 新版有安全校验，**拒绝从非公网 IP 下载** |
| **教训** | 排查网络问题**要往下钻一层**：不要只看报错，去验证"假设"（这里假设是 DNS，一测就实锤）。而且**一个现象能牵连全局**（连百度都中招 = 不是百度的锅） |
| **对策** | ① 临时退出代理；② 把 DNS 增强模式从 `fake-ip` 改成 `redir-host`；③ 直连不通则用 ModelScope 下 GGUF 再 `ollama create` 导入 |

## L02 · 模型回答"资料中未找到"，但它其实是对的 —— 入库质量才是命门

| 项 | 内容 |
| --- | --- |
| **现象** | 问"球阀的压力/温度范围"，RAG 回答"资料中未找到"。检索回来的全是**截止阀/闸阀/止回阀**的片段 |
| **排查过程** | ① 看检索到的原文 → 不是球阀内容；② 统计向量库 → 仅 12 个切片含 "BALL VALVE"，且都是公司简介；③ **直接解析源 PDF** → 9708 字里 `Pressure`/`PN`/`Class`/`ASME`/`API` **全部出现 0 次** |
| **根因** | 那个 PDF 抽出的 9708 字**全是每页重复的页眉页脚**（公司地址/电话/邮箱）。**真正的参数表是图片，不在 PDF 文本层里** |
| **教训** | ⭐ **RAG 第一定律：Garbage in, garbage out。** 检索的上限由**入库质量**决定，跟模型多强没关系。模型说"找不到"是**诚实**，不是幻觉，更不是 bug |
| **对策** | 上 OCR：把 PDF 页渲染成图 → 识别成文字，再入库 |

## L03 · "每页字符数 > 50 就算文本型" —— 这个启发式太天真

| 项 | 内容 |
| --- | --- |
| **现象** | 我写的判断规则把 `Ball Valve(2).pdf` 判为"文本型，可直接用"（430 字/页，看着挺多） |
| **根因** | 430 字/页**全是页眉噪音**，有效信息为 0。**字符数量 ≠ 有效信息量** |
| **教训** | ⭐ **不要用"数量"指标代替"质量"指标。** 判断"有没有内容"，要看**内容是不是你要的东西**（领域关键词命中），或者先去掉重复行再看剩余 |
| **对策** | 判断标准改为：**领域关键词命中数**（Pressure / PN / Class / Temperature / ASME / API / DN / 材质代号），命中 ≈ 0 就判为需要 OCR |

## L04 · 检索不准时的正确排查顺序

| 项 | 内容 |
| --- | --- |
| **教训** | ⭐ 出问题**别先怪模型**。RAG 的排查顺序是自下而上：<br>**① 入库**（资料真的抽出来了吗？）→ **② 检索**（召回的原文对不对？）→ **③ 生成**（提示词 / 模型） |
| **为什么** | 90% 的"答不好"死在①和②。模型是最后一环，它只能基于你给的资料回答。<br>本次就是典型：看着像"检索不准"，实际是"入库根本没收进去" |
| **实操** | 加一个 `--show` 参数把**检索原文**打出来 —— 这个功能值得每个 RAG 项目第一天就做 |

## L05 · 权限过滤必须在"检索之前"，不能是"检索之后再隐藏"

| 项 | 内容 |
| --- | --- |
| **教训** | ⭐ 如果先检索出机密资料、再在展示时隐藏，**模型在生成阶段已经"读"到了机密内容**，它可能一句话就泄露出去 |
| **正确做法** | 把权限翻译成**向量库的过滤条件**（`where`），让机密资料**根本不出现在候选集里** |
| **实现** | 每个切片入库时打元数据（`sensitivity` / `owner` / `team`），检索时按角色拼 `where` |

## L06 · 概念澄清：RAG ≠ 深度学习

| 项 | 内容 |
| --- | --- |
| **误区** | 以为做 RAG 就是"搞深度学习"、要训练模型 |
| **事实** | RAG **不训练任何模型**。它 = **已经训好的模型** + **检索你自己的资料**。你调的是推理（inference），不是训练（training） |
| **真正的"训练/微调"** | 那是另一条路（Fine-tuning / LoRA）：改变模型本身的"能力与风格"。和 RAG 解决的是不同问题 |
| **建议** | 先做 RAG（见效快、可控、可解释），等它通了再考虑要不要碰微调 |

## L07 · 中文提问 vs 英文语料：语义检索会"错位"

| 项 | 内容 |
| --- | --- |
| **现象** | 用中文问"球阀"，命中的却是其他阀门的英文 `Pressure Range` 片段 |
| **根因** | 向量是按**整体语义**匹配的。问题里的"压力和温度范围"这个语义，比"球阀"这个词更容易匹配到英文语料里的同类片段 |
| **教训** | ⭐ 跨语言语料里，**"意思相近"不一定等于"回答对了问题"**。实体（这里指产品名）往往才是关键 |
| **对策** | ① **查询改写**（中文术语 → 英文术语映射表，如 球阀→ball valve）；② **混合检索**（向量 + 关键词 BM25），让"Ball Valve"这种精确词也能命中 |

## L08 · 切片：段落优先 + 留重叠

| 项 | 内容 |
| --- | --- |
| **为什么切** | 模型有上下文窗口上限；检索是按"块"做的。整篇入库 → 重点被淹没；切太碎 → 句子被拦腰截断 |
| **关键参数** | `chunk_size`（块大小）与 `overlap`（相邻块重叠） |
| **实测演示** | 120 字块 + 20 字重叠时，第 2 块开头出现第 1 块结尾的内容（`00，适用温度 -29℃…`）—— 这就是 overlap 在起作用，防止跨块语义丢失 |
| **教训** | 切片**不要机械按固定字数硬切**，优先按**段落/标题**等语义边界切 |

## L10 · 重复噪音会"淹没"真正的知识，把检索带偏

| 项 | 内容 |
| --- | --- |
| **现象** | `Gate Valve1.pdf` 抽出 55995 字 → 生成 **134 个切片**，数量远超其他文件；检索时它频繁霸占前排，即便问题问的不是闸阀 |
| **排查** | 统计"去重后长度"：**只剩 1964 字**。也就是说 134 个切片里，**绝大部分是每页重复的页眉页脚** |
| **根因** | 页眉页脚每页都印一遍，切完片就变成"N 份几乎一样的噪音切片"。它们在向量空间里高度相似，**很容易压过真正的知识** |
| **教训** | ⭐ **入库前必须清洗**。相似度检索没有"重要性"概念，谁切片多谁嗓门大；不洗数据，等于让噪音投票 |
| **对策** | 入库前做**样板文字剔除**：统计行频次，把"出现 ≥3 次且不长"的行判为页眉页脚删掉；网址/邮箱/电话正则清洗 |

## L11 · 判断粒度要到"页"，不是"文件"

| 项 | 内容 |
| --- | --- |
| **现象** | `Ball Valve(2).pdf` 去重后仍有 7050 字"有效文本"，被判定为"文本型，不用 OCR"。但我们已知它**没有一处球阀参数** |
| **根因** | 这份 PDF 是**混合型**：**前几页是公司简介（真文字）+ 后面几页参数表（图片）**。按"整份文件"判断，就被前几页的真文字骗过去了 |
| **教训** | ⭐ **同一份文档里，有的页是文字、有的页是图片**。"文件级"的判断会漏掉真正需要 OCR 的页 |
| **对策** | 判断下沉到**页**：逐页看"这页的文本有没有规格关键词"，没词的页才送去 OCR。<br>工程上就是：**逐页决策，而不是逐文件决策** |

## L12 · OCR 能救回"图片里的知识"，但有速度和噪声两个代价（✅ 已实测跑通）

| 项 | 内容 |
| --- | --- |
| **验证** | 对 `Ball Valve(2).pdf` 第 3 页（原生文字 **0 字**、纯图片）做 OCR，识别出 **527 行**，包含：`GKV-243`、`3-WAY/4-WAY FULL BORE FLANGE END BALL VALVE`、`DN100~DN150`、**`GKV-243 PN16/40`**、**`TEMPERATURE RANGE: -20 to 180`**、**`PN16/40, Class150`**、**`BODY CF8M/CF8/WCB`**、**`TEST: EN-12266-1`**、`EN1092-1 TYPE21 PN16/40` |
| **结论** | ⭐ **知识一直在，只是藏在图片里。** pypdf 抽不到的参数，OCR 全捞回来了 —— L02/L11 的坑由此打通 |
| **代价①速度** | 200 dpi **CPU 约 8.9 秒/页**。一份 23 页文档 ≈ 3.4 分钟；855 个 PDF 全量 OCR 是"小时级"甚至更久的工程 |
| **代价②噪声** | OCR 会认错字符：`CONTROL` 被认成 `CONＴROL`（全角 T）、`3-WAY/4-WAY` 被认成 `3-WAYI4-WAY`（斜杠认成 I）。**检索时要容错**，别指望 100% 准确 |
| **对策** | ① **逐页决策**（`ocr.py`）：只有"文本层没用"的页才 OCR，能省掉大量页；② **GPU 加速**（onnxruntime-gpu，本机 RTX 4060 可提速数倍）；③ 多进程并行；④ 入库时对 OCR 文本做**规范化清洗**（全角→半角、常见误认替换） |

## L13 · 改了"解析器"却忘了改"调用方"，等于没改（✅ 已修正并验收）

| 项 | 内容 |
| --- | --- |
| **现象** | 逐页 OCR 解析器（`ocr.py`）写好了、单文件测试也通过了，但一入库，`Ball Valve(2).pdf` **仍然只有 19 块**，球阀参数依旧不见踪影 |
| **排查** | 看入库日志：该文件走的是"**文本型 → pypdf 直抽**"分支，**逐页解析器压根没被调用** |
| **根因** | 入库脚本的判断条件写的是"**只在 `needs_ocr` 时才走 OCR**"。而这个文件被**文件级判断**误判成"文本型"（就是 L11 那个坑）→ 逐页解析器**永远轮不到它** |
| **教训** | ⭐ **把能力做出来 ≠ 让它生效。** 改了解析逻辑，必须同步改"**谁来决定用哪个解析器**"。排查时要看**调用链**，不能只盯着模块本身 |
| **对策** | 入库逻辑改为「**所有 PDF 一律走逐页解析**」：文本页直抽、图片页 OCR。修正后 `Ball Valve(2).pdf` **19 块 → 55 块** |
| **验收** | 同一个问题：「球阀的工作压力和温度范围是多少？」<br>改造前 → 答"资料中未找到"；<br>改造后 → **准确作答 + 带出处引用**（来源正是之前抽不出字的 `Ball Valve(2)/(3).pdf`）。**阶段一闭环打通** ✅ |

## L14 · 让 OCR 真正用上 GPU，有四道坎（✅ 已打通）

| 项 | 内容 |
| --- | --- |
| **现象** | 装好 `onnxruntime-gpu`，`get_available_providers()` 也列出了 `CUDAExecutionProvider`，但 **OCR 速度纹丝不动**（GPU 9.3s vs CPU 9.4s） |
| **坎① 版本必须对上** | `onnxruntime-gpu 1.31` 要求 **CUDA 13**，本机驱动只到 CUDA 12.7 → `Failed to create CUDAExecutionProvider. Require cuDNN 9.* and CUDA 13.*`。**降到 1.22.0**（要 CUDA 12）解决 |
| **坎② CUDA 运行库可以只用 pip 装** | **不用装几个 G 的 CUDA Toolkit** —— `pip install nvidia-cudnn-cu12 nvidia-cublas-cu12 nvidia-cufft-cu12 nvidia-curand-cu12 nvidia-cuda-runtime-cu12` 即可（都落在 `site-packages/nvidia/*/bin`） |
| **坎③ DLL 搜索路径必须注册** | 不注册就报 `Could not locate cudnn_engines_tensor_ir64_9.dll` → `CUDNN_BACKEND_API_FAILED` → **静默回退 CPU**。三步都要做：`os.add_dll_directory()` ＋ 追加进 `PATH` ＋ **ctypes 显式预加载**（底层库在前、cudnn 在后） |
| **坎④ RapidOCR 的 GPU 参数有坑** | 只传 `use_cuda=True` 会被**忽略**（配置项其实叫 `det_use_cuda`/`cls_use_cuda`/`rec_use_cuda`）；而只传 `det_use_cuda=True` 又会**崩**（它内部要读 `model_path`）→ **必须连模型路径一起传** |
| **效果** | 单页推理 9.05s → **4.41s**（约 **2 倍**）；整份 23 页文档 OCR 126s → **106s**（约 19%，因为渲染/后处理仍是 CPU） |
| **教训** | ⭐ **"装上了"≠"跑起来了"。** GPU 加速的每一环（版本 / 库 / 路径 / 参数）错一个，都会**静默退回 CPU**——不报错，只是"没变快"。**验证提速必须实测计时**，不能只看 `get_available_providers()` |

## L15 · 多进程提速：四个"看不见的坑"（✅ 已跑通，74 页 515s → 285s）

| 项 | 内容 |
| --- | --- |
| **目标** | 855 个 PDF 全量入库，单线程跑要十几小时，必须并行 |
| **坑① 线程互相抢** | 每个进程默认吃满所有 CPU 线程，6 进程 × 12 线程 = 72 个线程抢 12 个核。实测不限制时，6 进程跑 74 页要 **515 秒** —— 和单进程几乎没区别，等于白并行 |
| **坑② 数学库也在偷偷开线程** | 不只 onnxruntime！**OpenBLAS / MKL / OpenMP** 各自都会按 CPU 核数建线程池，每个线程都要预留内存缓冲区。6 个进程叠起来直接把虚拟内存榨干：`OpenBLAS error: Memory allocation still failed after 10 retries` |
| **坑③ 环境变量设晚了等于没设** | 上面这些库是**在 import 的那一刻**读环境变量来决定线程数的。所以在子进程函数体里设没用，**必须在启动子进程之前设好**，靠进程继承传下去 |
| **坑④ 僵尸进程会污染后续所有测试** | 任务被中断时，`TaskStop` 只杀了外层父进程，**子进程全部残留**。累积了 **14 个僵尸进程、占掉约 5GB 内存**，导致之后每次测试都报内存分配失败。**看起来像"代码有 bug"，其实是环境被污染了** —— 排查性能问题前，先确认环境干净 |
| **成果** | 6 进程并行：**515 秒 → 285 秒**（74 页，1.8 倍）；单页 6.0s → **3.85s** |
| **附带发现** | `--workers 4 --gpu`（多进程共抢一块显卡）**会严重退化**：26 分钟都跑不完。**多进程走 CPU、单进程走 GPU**，各用各的才不会互相拖 |
| **教训** | ⭐ **并行不等于"多开几个进程"。** 线程数、库的隐式线程池、环境变量生效时机、僵尸进程残留 —— 任何一环没管住，结果都可能是"开了 6 个进程却一点没变快"，甚至更慢 |

## L16 · 跑大规模任务时，我被自己"骗"了两次（✅ 已修正）

| 项 | 内容 |
| --- | --- |
| **场景** | 全量入库 1307 个文件，跑 57 分钟，中途**两次**"看起来卡死" |
| **误判① 块缓冲** | 子进程的 stdout 接的是**管道**（不是终端），Python 会自动切成**块缓冲** —— 日志要攒够好几 KB 才落盘。表现：日志十几分钟一动不动。<br>**真相是输出还堵在缓冲区里**。<br>修法：给子进程加 `PYTHONUNBUFFERED=1`（我先前只给日志文件设了行缓冲，压根管不到子进程） |
| **误判② worker 把 CPU 吃光了** | 6 进程 × 2 线程 = 12 线程，占满全部 12 个逻辑核心 → **主进程**（做 embedding、写向量库）和 **ollama** 抢不到 CPU。<br>表现：OCR 缓存暴涨 175 个、入库日志几乎不动（"工人拼命生产、成品堆在仓库没人入库"）。<br>修法：`usable = cpu_count - 2`，**留 2 个核心给主进程和 ollama** |
| **顺带修复③** | 加了**断点续跑**：启动时先读向量库已有的 `source` 集合，跳过已完成文件（本次跳过 434 个，待处理从 1237 → 803） |
| **排查教训** | 判断"卡死"不能只看日志！要**同时看 CPU**：<br>· 日志不动 + CPU 高 = 在算（正常）<br>· 日志不动 + CPU 低 = 真卡死<br>· 还得先排除"是不是输出被缓冲了" |
| **教训** | ⭐ **观测工具本身会失真，失真会让我得出完全错误的结论。** 日志缓冲、CPU 争抢这类"看不见的中间层"，能让一个健康运行的任务看起来像死了。**排查之前，先确认"我的观测手段可靠吗"** |

## L17 · "图纸 / 照片型" PDF 是 OCR 的终极杀手（✅ 已加时间预算）

| 项 | 内容 |
|---|---|
| **现象** | 全量跑时卡在第 451 个，**11.5 分钟零产出**，CPU 却 100% |
| **第一层误判** | 以为是"主进程被 worker 饿死"（降并发到 4 进程）—— 有改善但没根治 |
| **真正元凶** | 卡住的是这类文件：`工厂布局图及照片.pdf`、`财务报表.pdf`、`XXX图纸.pdf` |
| **为什么** | RapidOCR 会先做"文字检测"= 在整张图上找**所有疑似文字框**。工程图纸（A1/A0 大图、密密麻麻的尺寸标注）和照片，会被检测出**成百上千个候选框**，然后逐个识别 → **单个文件能烧掉 800 秒 CPU** |
| **关键认知** | ⭐ **"文件大小"和"OCR 难度"完全无关**。0.05 MB 的 `组织机构图.docx` 能卡死，6.6 MB 的图纸也能卡死；难度只取决于"这张图上有多少个疑似文字框" |
| **对策 1** | 限制检测框上限 `det_limit_side_len` 相关阈值（1000 → 300）—— 顺带**把单页 OCR 提速一倍**（8.75s → 4.6s） |
| **对策 2** | **单文件时间预算**（默认 180 秒）：超时就放弃剩余页、保留已识别的部分。宁可少拿一点，也不能让一个坏输入拖垮整条流水线 |
| **对策 3** | 跳过 macOS 垃圾文件（`._` 开头）—— 全库里混着 70 个 |
| **教训** | ⭐ **长任务必须给"单个单元"设预算上限。** 批处理系统里，一条坏数据造成的损失不是"1 条"，而是"整条流水线停摆"。**超时、限流、熔断，不是优化，是必需品。** |

## L18 · 切片上万后，`col.get()` 全量读取会崩（✅ 已改分页）

| 项 | 内容 |
|---|---|
| **现象** | 入库到 4 万切片后，统计脚本报 `chromadb.errors.InternalError: too many SQL variables` |
| **原因** | Chroma 底层是 SQLite。一次性 `col.get()` 拉全部元数据，会生成一条含**几万个 `?` 占位符**的 SQL；SQLite 有变量个数上限，直接拒绝执行 |
| **为什么之前没事** | 切片只有几百 ~ 一万时没到上限，所以"一直能用"，直到规模上来才暴露 |
| **修法** | **分页读取**：`col.count()` 拿总数，然后 `col.get(limit=4000, offset=N)` 循环累加 |
| **教训** | ⭐ **小数据量能跑通 ≠ 方案正确。** 很多设计缺陷只在规模上来后才显形（这个坑和"批量任务里一条坏数据拖垮全流水线"是同一类问题）。**做统计/导出/遍历这类操作时，默认就该分页**，别等它崩。 |

## L19 · 给文档做「版本管理」比想象中难 —— 五个坑（✅ 已落地）

**背景**：用户提的真实需求 —— *"26 年换了供应商，新价格表必然和老价格表冲突，检索就会答错。"*
方案见 `docs/versioning.md`。落地时踩了这些：

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| ① | **"年份范围"被当成文档日期** | `REFERENCE LIST ... 2019~2022.pdf` 判成 2019 年 —— 那是**项目跨度**，不是文档日期 | 识别 `YYYY~YYYY`，取较晚那年（2022），来源标 `filename-range` |
| ② | **范围又被当成版本后缀** | 上面那份的家族变成 `reference list in different field 2019`（`-2022` 被当版本号剥掉了） | 归一化前先把年份范围整体抹掉 |
| ③ | **把"重复"当成了"版本取代"** | 第一版逻辑"同族最新的算 active、其余 superseded" → **174 个被标作废**；实际其中 **169 个是内容完全相同的副本**（同一份文件散落在 `产品资料` / `报价单/xxx` / `工作home/开发信资料` 三处） | 先算**内容指纹**：指纹相同 → `duplicate`；只有「内容不同 + 日期可信 + 相差 ≥30 天」才判 `superseded` |
| ④ | **子集判定会出错** | 按单个子目录入库时，status 只在该子集内比较 → 明明是副本的文件被判成了 active | status 必须**基于全量文件**判定，调用方要传全量列表 |
| ⑤ | **同一个坑复现** | 断点续跑里又写了一次 `col.get(include=["metadatas"])` → 再次撞上 **L18 的 SQL 变量上限** | 抽成统一的分页读 |
| ⑥ | **只在"家族内"去重会漏掉一半** | 同一份文件被**改名**后家族就分开了：`产品资料/Ball Valve(3).pdf` 与 `报价单/xxx/Ball Valve(cast).pdf` **内容完全一致**，却都被判 active。全库实测漏掉 **55 组 / 61 个副本** | 去重改为**全局按内容指纹**（跨家族）；主副本优先选「人工保留 > `产品资料/` 目录 > 路径短」 |

**教训**：

- ⭐ **"哪一版作数"是业务决策，程序不该擅自判死。** 只自动处理"铁证"情形
  （内容不同 + 日期可信 + 差距明显），其余一律列成「待裁决冲突」交给人。
- ⭐ **内容相同 ≠ 新版本。** 判版本关系**必须先看内容指纹**，
  否则会把大量重复文件误判成"已作废"，**凭空丢掉知识**。
- ⭐ **修了一个地方 ≠ 消除一类问题。** L18 的 SQL 上限在几十行之外又犯一次，
  才想到该抽成公共函数。
- ⭐ **"归类"决定了"去重"的边界。** 只要去重是"分组的副产品"（按家族去重），
  分组一变，去重就漏。**去重应该按内容本身（全局指纹）做**，与分组解耦。
- ⭐ **一个文件不该霸占检索名额。** 一份几十页的手册会产生几十个切片，
  语义检索会把它一堆段落全排前面，把别的资料挤下去
  → 加「同一文件最多 N 条」（`--max-per-doc`，默认 2）。
  实测：6 条结果从"只覆盖 3~4 个文件"变成"**覆盖 6 个不同文件**"。

**成果**（本项目实测）：
- 1232 个文件全部打上 **日期 / 版本号 / 文档家族 / 状态 / 内容指纹**
- 最终状态分布：`active` **901** · `duplicate` **210** · `rejected` **117**（人工否决）· `superseded` 4
- 检索**默认只命中当前有效版本**；`--as-of YYYYMMDD` 可做时间旅行
- 回填 4.2 万个切片仅耗时 **18 秒**（不重跑 OCR、不重算向量）
- 人工裁决 101 个冲突家族后：**版本冲突归零**，时效健康分 **89 / 100**

**额外发现**：**资料重复率 13%**（165/1232）——同一份产品册/证书在多个目录各存一份，
检索时会重复占用排名、稀释其他内容的曝光。这也是一种"噪音"。

## L20 · 没有评测集，所有优化都是盲改（✅ 已建评测集并验证）

**背景**：用户让"加固现有能力"，我列了 6 项短板（解析/价格/参数检索/评测/一致性…），
用户选了"先做评测集"。做完之后立刻证明了这个选择是对的。

### 做了什么

- **`eval/golden_set.jsonl`**：20 题评测集（产品参数 12 / 报价 5 / 通用 3）。
  **铁律：答案全部来自我亲自核对过的资料，绝不编造。**
- **`scripts/run_eval.py`**：单题评测（文件召回 + 关键词命中）
  + **3 项系统底线检查**（版本隔离 / 权限隔离 / 时间旅行）
  + 基线对比（`--save-baseline`，之后每次跑自动出"↑/↓"）。
- 评测走**生成环境的同一条代码路径**（同一个 `hybrid_query`），否则数字不反映真实表现。

### 数字（一轮改动的真实收益）

| 指标 | 基线 | 修复后 | 变化 |
|---|---|---|---|
| 文件召回率 | 54.5% | **72.7%** | **+18.2pt** |
| 关键词命中 | 79.0% | **89.5%** | **+10.5pt** |
| 产品参数类 · 关键词 | 90.9% | **100%** | +9.1pt |
| 失败题目数 | 4 条 | **2 条** | — |

### 关键过程：评测集一跑，就抓到了"同一个根因的第二次现身"

基线里 `P02「GKV326 闸阀符合什么标准」` 检索到的是 `报价单/20260319某地区/20260319-V.docx`，
而不是 `产品资料/Gate Valve1.pdf`。

—— 这正是我在写**技术规格书**时发现、并已经修好的问题：**语义检索对型号不敏感**。
但当时我只改了 `make_spec.py`，**`ask.py`（主问答）还在用老逻辑**，于是同一个错误原样复现。

修复方式：**把它抽成公共模块 `src/search/hybrid.py`**（精确标识匹配 + 语义召回 + 文件限流），
`ask.py`（问答）与 `make_spec.py`（规格书）共用 —— 而不是在每个调用点各修一遍。

### 教训

- ⭐ **没有度量就没有优化。** 改之前先建尺子；否则"变好了"只是感觉。
  这次改动之所以可信，是因为有 **54.5% → 72.7%** 这组数字，而不是我说"应该好些了"。
- ⭐ **同一个根因会在多个模块复现 —— 这是"修了一处 ≠ 修了全部"的第二次教训**
  （第一次是 L18 的 SQL 上限在另一个函数里复发）。
  **正确做法不是逐个调用点打补丁，而是把能力抽成公共模块。**
  同一个错误犯两次，说明它不是疏忽，而是**方法问题**：改完要问一句
  *"还有谁在用旧逻辑？"* 和 *"这个能力该不该抽出来？"*
- ⭐ **评测集的答案必须是"核对过的真事"**，不能编造。
  编造答案的评测集比没有更糟 —— 它会给出虚假的安全感，把错误的方向验证成"有效"。
- ⭐ **评测必须跑生产同一条代码路径**，否则测的是另一个系统。

### 仍然失分的两题（诚实的短板）

- `R04「某地区发电厂项目的阀门报价涉及哪些型号？」`、`G03「产品宣传册里的工作温度范围」`
  —— 这两题**没有具体型号**，属于**纯语义检索的局限**（"项目名""宣传册"这类概念没被准确定位）。
  下一步的解法是 **BM25 关键词混合检索 / Rerank**，而不是精确匹配。

## L21 · "我记得"不可靠，"查一下"才可靠（✅ 已修正）

**场景**：RAG 项目做完脱敏后，我告诉用户"需要你手动推到 GitHub"。

用户反问：

> **"github 简历里的其他项目就是你帮我上传到 github 里的，为什么这个项目要我手动推？"**

**查证结果：用户是对的。**

- 用 `conversation_search` 检索历史，找到 **3 天前**的会话记录：
  "AI：…部署作品集与 GitHub → 重构成 4 工作流集合；结果：简历、作品集、GitHub 三件套均完成投递态"
- 本地还留着那次的仓库：`Desktop\求职\openclaw-leadgen-workflow`
  - remote 指向 `github.com/VankoTing/ai-workflows-for-trade.git`
  - 里面**已经有一个 `04-knowledge-base-rag/` 目录**，放的正是我当时写的「规划版 README」
  - 甚至还有我自己写的 `如何发布到GitHub.md`，里面写明"第一次 push 会弹登录窗口"

**三层线索我都没先看，仅凭"`gh` 命令没装"这一个信号就下了结论。**

第二个错误更隐蔽：我用 `git credential fill` 探测"有没有 GitHub 凭证"，
它返回空 → 我据此判断"推不了"。**结果 `git push` 一次就成功，连弹窗都没有。**

**教训**：

- ⭐ **接手任务前先查"这件事以前做过没有"。** 三个成本极低的动作：
  检索历史会话、看相关目录、找有没有前人（哪怕是自己）留下的说明文档。
- ⭐ **判断"能不能做"，要试，不要推。**
  间接探测（`git credential fill` 返回空）≠ 实际能力（`git push` 真的成功）。
  **与其告诉用户"这需要你来做"，不如先试一次** —— 试的成本，远低于让用户返工的代价。
- ⭐ 这两个错误叠加起来，等于**把本该自己干的活推给了用户**。
  这比技术错误更值得警惕：**技术错误会报错，推诿不会。**

## 📌 十句话总结（如果只记十件事）

1. **Garbage in, garbage out** —— 入库质量决定检索上限。
2. **排查自下而上** —— 先看入库、再看检索、最后才怀疑模型。
3. **数据先洗再用** —— 页眉页脚噪音会淹没知识，判断粒度要细到"页"。
4. **权限在检索前生效** —— 看不到的，压根不让它被检索到。
5. **做出来 ≠ 生效** —— 改了模块要改调用方；装了 GPU 要实测确认真的用上。"静默退回"是最贵的坑。
6. **长任务要有"单元预算"** —— 一条坏数据不该拖垮整条流水线；超时、限流、熔断是必需品。
7. **小数据能跑 ≠ 方案正确** —— 规模上来才暴露设计缺陷；遍历/统计/导出一律默认分页。
8. **知识会过期，"哪版作数"要交给人** —— 程序只做铁证判定（内容不同+日期可信），
   其余列成待裁决；且**判版本前必须先看内容指纹**，否则会把重复文件误判成作废、凭空丢知识。
9. **先建尺子，再谈优化** —— 没有评测集，"变好了"只是感觉。
   工具：20 题黄金集 + 3 项系统底线检查；改一次跑一次，用 ↑/↓ 说话。
10. **"我记得"不算数，"查一下"才算** —— 动手前先查历史会话 / 相关目录 / 说明文档；
    判断能不能做要**试一次**，别用间接信号推断后就把活推给用户。
